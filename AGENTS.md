# AGENTS.md

This file provides guidance to AI coding agents when working with code in
this repository.

## Overview

This repository is the Ansible collection `alexbarton.boilerplate` ("ABC",
Ansible Boilerplate Collection). It is not a regular Ansible project: it ships
template files, scripts, playbooks and Makefile fragments that *other* projects
install via Ansible Galaxy into `ansible_galaxy/ansible_collections/` and then
build upon. Keep this dual role in mind: many files in the repository root are
both the configuration of this repository and the templates copied into
dependent projects.

## Contributing

Read `CONTRIBUTING.md` first: it describes the development setup, the `make`
targets and checks (`make check` is the test gate), the requirements for
changes including the shell script conventions, and the rules for AI-assisted
contributions. All of it applies to agents as well.

The release process is documented in `docs/how-to-release.md`; the version
number lives in `galaxy.yml`, `pyproject.toml`, and as the minimum collection
version in the `requirements.yml` template generated by `bin/abc`. The minimum
versions of `ansible-core` and `ansible-lint` are defined in `pyproject.toml`,
`meta/runtime.yml` and `ABC_PYTHON_DEPS` in `bin/abc`, and new roles get
`min_ansible_version` from `libexec/abc-new`: keep them in sync.

## Architecture

### `abc` stub and backend

- `bin/abc` is a self-contained *stub* script. It is copied (not linked) into
  dependent projects so it works before the collection is installed, and
  therefore must not depend on any other file of the collection. It
  bootstraps a virtual environment (`uv` preferred, Python `venv` + `pip` as
  fallback), installs the collections from `requirements.yml` (location
  overridable via `BOILERPLATE_COLLECTION_SRC`), and then delegates everything
  else to `libexec/abc.backend` inside the installed collection
  (`ABC_BASE_D`, by default
  `ansible_galaxy/ansible_collections/alexbarton/boilerplate`).
- Because `bin/abc` must be self-contained, the detection of the tools and the
  setup of the Python virtual environment exist twice: in `bin/abc`
  (`Venv_Init_*`) and in `libexec/abc.backend` (`Venv_Update_*`). Change both
  places together; the comments marked "Keep in sync" point to them.
- `libexec/abc.backend` implements the built-in commands (install, init,
  update, ...) and dispatches all other subcommands to *plugins*: executable
  `abc-<name>` files found in `./libexec`,
  `/usr/local/libexec/ansible-boilerplate/`,
  `/usr/local/lib/ansible-boilerplate/`, `${ABC_BASE_D}/libexec` and
  `/usr/libexec/ansible-boilerplate/` (first match wins). A plugin's help text
  comes from its `# description=...` header comment.
- `bin/a`, `bin/ap`, `bin/aps` are thin wrappers around `ansible` and
  `ansible-playbook`; they are symlinked into dependent projects (see
  `docs/scripts.md`).

### Templates for dependent projects

`abc init` copies `.ansible-lint`, `.editorconfig`, `.gitignore`,
`.vscode/settings.json`, `.yamllint.yml` and `ansible.cfg` from the collection
into a new project. `abc update` only refreshes those of these files that
already exist in the project; when the project's copy differs, the new version
is written next to it as `<file>.new` instead of overwriting it. Changes to
these files therefore affect every dependent project. `Makefile.boilerplate` is
included by the generated project `Makefile` (see `libexec/abc-generate`); the
top-level `Makefile` here wraps it and adds the repository-specific targets.

`ansible.cfg` sets `collections_path = ansible_galaxy` and
`roles_path = ansible_galaxy/ansible_roles:roles`; the scripts depend on these
paths. `hosts.ini` and `site.yml` exist only for local checks and are excluded
from the built archive (`build_ignore` in `galaxy.yml`).

`README.md` is also the collection's page on Ansible Galaxy (`readme` in
`galaxy.yml`), so keep it suitable for that audience.

## File Formatting

Follow the project's existing conventions first: formatter and linter
configuration (`.editorconfig`, `.yamllint.yml`, `.ansible-lint`,
`.mdl-rules.rb`), then the style of the surrounding code. Where nothing is
defined, keep lines within 80 columns (`.yamllint.yml` allows up to 100 in YAML
files, with a warning).

Wrap prose in text files at 80 columns. Don't wrap code, tables, URLs, or other
lines that would break if split.

Markdown:

- Leave a blank line below every heading.

## Version Control

If a `.jj` directory is present, the clone is a colocated Jujutsu/Git repo:
use `jj` rather than mutating `git` commands then.

### Commits

- Subject: imperative mood, capitalized, no trailing period, ≤ 50 characters
  (72 at most).
- Blank line between subject and body; wrap the body at 72 columns.
- Body explains what changed and why, not how.
- One logical change per commit.

End the description of commits made with AI assistance with a trailer naming
the model that was actually used, separated from the body by a blank line:

```text
Co-authored-by: <model name> <vendor no-reply address>
```
